1. Project Overview
The Peer Learning and Tutoring System is a web-based platform developed as a Year 3 IT project for SLIIT. The platform connects university students who need academic help with peer tutors who can provide it. The system manages the full tutoring lifecycle from tutor discovery and booking through to live sessions, payments, ratings, and session recordings.

The project addresses a real university student need: reducing the friction in finding, booking, and learning from peer tutors. It replaces manual coordination via WhatsApp or email with a structured, feature-rich platform.

3. System Actors
The system has three main actors, each with a distinct role and set of permissions.

Admin
•	Manages all users — approve, edit, deactivate accounts.
•	Views all bookings, payments, and platform activity.
•	Downloads PDF reports: user lists, booking summaries, revenue analytics.
•	Deletes inappropriate content (session notes, messages) with reason logging.
•	Monitors tutor verification status and platform health.

Tutor
•	Registers and sets up a profile with subjects, bio, and hourly rate.
•	Awaits admin verification before becoming searchable.
•	Manages availability calendar — adds and removes time slots.
•	Accepts or rejects student booking requests.
•	Participates in live sessions via real-time chat.
•	Submits session notes after each completed session.
•	Receives payments automatically after session completion.

Student
•	Registers and browses verified tutors by subject.
•	Views tutor availability and submits booking requests.
•	Pays for sessions via Stripe before confirmation.
•	Joins live sessions and uses real-time chat and file sharing.
•	Reads session notes submitted by the tutor.
•	Rates and reviews the tutor after session completion.
•	Views upcoming sessions and learning history from dashboard.
 
4. Module Breakdown by Member
The project is divided into five modules. Each member owns one module end-to-end — from database stored procedure through to UI screens.

Shared — Authentication, Payment & Reports
This layer is used by all members and is not owned by a single person. It provides the foundation that every module depends on.

Feature	Description
User Registration	Students and tutors self-register. Admin registers via DB only.
Login (JWT)	Email + password login. Returns a JWT token used for all protected API calls.
Google OAuth 2.0	Login or register using a Google account. Auto-creates profile on first use.
Forgot Password	3-step flow: request OTP via email, verify OTP, reset password.
Email Verification	Verification email sent on registration. Account locked until verified.
Role-Based Access	Admin / Tutor / Student roles enforced at controller and stored procedure level.
Stripe Payment	Student pays for session. Stripe webhook auto-syncs payment status.
PDF Invoice	Small PDF invoice auto-generated after successful payment.
Admin Reports	Downloadable PDF reports: users, bookings, revenue, top tutors.

CRUD	Action	Business Rule

READ	Browse tutors	Only Active and Verified tutors appear in search results.
UPDATE	Edit profile / rate	Tutor can edit own profile only. Admin can edit any.

Member 2 — Session Booking & Scheduling

•	Email confirmation sent to both student and tutor on booking confirmation.

•	Cancellation push notification sent immediately to the other party.

7. Key Business Rules
Business rules are functional conditions that control how each UI operates. They must be specific and testable as per IT3040 requirements.

7.1 Access Control Rules
•	Only Admin can: approve/reject tutors, delete any content, download reports, view all users.
•	Only Tutor can: submit session notes, manage own availability, accept/reject bookings.
•	Only Student can: create bookings, submit ratings, access own recording playback.
•	Both Student and Tutor can: send messages, upload files, view their shared session data.

7.2 Validation Rules
•	Booking date must be in the future. Duration must be between 30 and 180 minutes.
•	File uploads limited to PDF, DOCX, PNG, JPG. Maximum file size is 5MB.
•	Star rating must be between 1 and 5. Review text is optional.
•	Password minimum 8 characters. Email must match SLIIT format for tutors.
•	OTP code expires after 10 minutes. Can only be used once.

7.3 Workflow Rules
•	Booking status flow: Pending → Confirmed → Active → Completed (or Cancelled at any stage before Active).
•	Tutor profile status flow: Pending → Active (or Suspended by admin).
•	Availability slot status: Free → Booked (on confirmation), Booked → Free (on cancellation).
•	Session note is locked 24 hours after submission. Student cannot read it until session is Completed.
•	In-session messages can only be edited within 5 minutes of sending.
•	Out-session messages can only be edited within 30 minutes of sending.

7.4 Capacity & Limit Rules
•	One booking per student per tutor per time slot — no duplicate bookings.
•	One session note per booking — tutor cannot submit multiple notes.
•	One rating per booking — student cannot rate the same session twice.
•	Session recordings expire after 30 days and become inaccessible.

7.5 Notification & System Response Rules
•	Student receives email and SignalR notification when tutor accepts or rejects booking.
•	Both parties receive a session reminder 24 hours before start time.
•	Payment confirmation email with PDF invoice sent immediately after successful Stripe payment.
•	Admin receives alert when a new tutor registers and awaits verification.
